팀 프로젝트에서 인증을 맡으면서 세션 쿠키 방식을 선택하게 되었습니다.  
구현을 시작하기 전에, **이 방식이 애초에 무엇을 어떻게 하는 것인지** 부터 정리해 두려 합니다.

이 글에는 특정 프레임워크가 등장하지 않습니다. HTTP 헤더 수준에서 무슨 일이 벌어지는지만 다룹니다.  
Spring Security로 이걸 실제로 구현하는 과정은 다음 글에서 따로 정리하겠습니다.

---

## 1. HTTP는 상태를 기억하지 않는다

모든 것의 출발점은 이 한 문장입니다.

> HTTP는 무상태(stateless) 프로토콜이다.

서버 입장에서 요청 하나하나는 완전히 독립적입니다. 방금 로그인 요청을 처리했더라도, 1초 뒤에 도착한 다음 요청이 **같은 사람이 보낸 것인지 알 방법이 없습니다.**

```http
POST /login       → 로그인 성공을 응답
GET  /dashboard   → "당신 누구세요?"
```

두 요청 사이에는 아무런 연결고리가 없습니다. TCP 커넥션이 재사용되더라도 그건 전송 계층의 이야기일 뿐, HTTP는 그것으로 신원을 판단하지 않습니다.

그래서 필요한 것이 **"아까 그 사람"임을 증명할 표식**입니다. 이 표식을 매 요청마다 실어 보내는 수단이 쿠키이고, 그 표식이 가리키는 정보를 서버가 들고 있는 방식이 세션입니다.

---

## 2. "세션이냐 쿠키냐"는 잘못된 질문이다

처음 공부할 때 가장 헷갈렸던 부분입니다. 검색하면 "세션 vs 쿠키" 라는 제목의 글이 쏟아지는데, **둘은 대립 관계가 아닙니다. 층위가 다릅니다.**

- **쿠키** — 브라우저가 요청에 자동으로 실어 보내는 **전달 수단**
- **세션** — 서버가 사용자 상태를 보관하는 **저장 방식**

세션 방식은 쿠키를 **도구로 써서** 세션 ID를 전달합니다. 즉 세션 방식에는 보통 쿠키가 포함되어 있습니다. 둘 중 하나를 고르는 게 아닙니다.

실제 선택축은 두 개이고, 서로 독립적입니다.

| | 쿠키로 전달 | 헤더로 전달 |
| --- | --- | --- |
| **서버가 상태 보관 (세션)** | 이 글이 다루는 방식 | 가능하지만 드뭅니다 |
| **토큰에 상태를 담음 (JWT)** | 가능하며 흔합니다 | 가장 흔한 JWT 구성 |

"무엇으로 전달하는가"와 "상태를 어디에 두는가"는 각각 따로 정하는 문제입니다. 이 글은 표의 좌상단, **서버가 상태를 갖고 쿠키로 식별자만 전달하는** 방식을 다룹니다.

---

## 3. 쿠키: 브라우저가 대신 들고 다니는 메모지

쿠키의 동작은 헤더 두 개로 끝납니다.

서버가 응답에 `Set-Cookie`를 실어 보내면,

```http
HTTP/1.1 200 OK
Set-Cookie: SESSIONID=8f2a...c91; Path=/; HttpOnly; SameSite=Lax
```

브라우저는 이를 저장해 두었다가, **같은 출처로 가는 이후 모든 요청에 자동으로** 붙여 보냅니다.

```http
GET /dashboard HTTP/1.1
Host: example.com
Cookie: SESSIONID=8f2a...c91
```

여기서 **"자동으로"** 라는 점이 핵심입니다. 개발자가 코드로 붙이는 게 아니라 브라우저가 규칙에 따라 붙입니다. 이 성질이 뒤에서 장점(4절)이자 동시에 약점(8절)으로 돌아옵니다.

**① 로그인 요청** — 사용자가 아이디와 비밀번호를 보냅니다.

**② 서버가 검증 후 세션 생성** — 서버는 비밀번호를 확인하고, **자기 쪽 저장소에** 이 사용자의 상태를 기록합니다. 위 시뮬레이터에서 "세션 저장소" 칸에 새 행이 생기는 순간이 이것입니다.

**③ 세션 ID만 쿠키로 발급** — 응답에는 세션 ID라는 **열쇠 번호만** 담깁니다. 사용자 정보는 나가지 않습니다. `Set-Cookie` 줄이 초록색으로 강조된 이유가 이 값이 앞으로 모든 인증의 근거가 되기 때문입니다.

**④ 이후 요청** — 브라우저가 쿠키를 자동으로 붙여 보내면, 서버는 그 ID로 저장소를 조회해서 "아 42번 사용자군" 하고 알아봅니다. `Cookie` 헤더 옆에 "브라우저가 자동으로 첨부"라고 적어둔 이유는, 이 값을 개발자가 코드로 붙인 게 아니라는 점이 3절의 핵심이기 때문입니다.

정리하면 이렇습니다.

| | 브라우저가 가진 것 | 서버가 가진 것 |
| --- | --- | --- |
| 세션 방식 | 세션 ID (의미 없는 문자열) | 사용자 정보 전체 |
| 토큰 방식 | 사용자 정보가 담긴 토큰 | (원칙적으로) 아무것도 없음 |

**세션 방식에서 쿠키에 담기는 값은 그 자체로 아무 의미가 없습니다.** 보관함 번호표일 뿐이고, 내용물은 서버에만 있습니다. 이 구조에서 파생되는 성질들이 아래 절들의 내용입니다.

---

## 5. 세션 ID는 추측할 수 없어야 한다

번호표만 있으면 누구든 보관함을 열 수 있으므로, **세션 ID를 훔치거나 맞히는 것이 곧 로그인**입니다. 그래서 세션 ID에는 두 가지 요구사항이 따라붙습니다.

**충분한 길이와 예측 불가능성.** 순번(`1`, `2`, `3`...)처럼 규칙이 있으면 남의 세션을 그대로 입력할 수 있습니다. 암호학적으로 안전한 난수여야 합니다.

**로그인 시점의 ID 재발급.** 이건 **세션 고정 공격(Session Fixation)** 에 대한 대응입니다. 공격자가 자기가 아는 세션 ID를 피해자 브라우저에 미리 심어 두고, 피해자가 그 상태로 로그인하면, 공격자는 이미 알고 있던 ID로 로그인된 세션에 올라탑니다.

대응은 단순합니다. **로그인에 성공하는 순간 기존 세션을 버리고 새 ID를 발급하면** 공격자가 심어둔 ID는 무효가 됩니다. 대부분의 서버 프레임워크가 이 동작을 기본 제공합니다.

---

## 6. 쿠키 속성: 이 값들이 곧 보안 설정이다

`Set-Cookie`에 붙는 속성들은 장식이 아니라 방어 수단입니다.

| 속성 | 역할 |
| --- | --- |
| `HttpOnly` | JavaScript에서 쿠키 접근을 차단합니다. XSS가 발생해도 `document.cookie`로 세션 ID를 긁어갈 수 없습니다 |
| `Secure` | HTTPS 연결에서만 전송합니다. 평문 통신 구간에서 탈취되는 것을 막습니다 |
| `SameSite` | 다른 사이트에서 출발한 요청에 쿠키를 붙일지 결정합니다 (8절) |
| `Domain` / `Path` | 쿠키가 전송될 범위를 제한합니다. 넓을수록 노출면이 커집니다 |
| `Max-Age` / `Expires` | 쿠키 자체의 수명입니다 (7절) |

`HttpOnly`는 특히 짚고 넘어갈 만합니다. **토큰을 브라우저 저장소(`localStorage`)에 두는 방식과 비교되는 지점**이기 때문입니다. `localStorage`는 정의상 JavaScript로 읽는 저장소라 XSS 앞에서 그대로 노출되지만, `HttpOnly` 쿠키는 브라우저가 스크립트의 접근 자체를 거부합니다.

---

## 7. 만료: 서로 다른 세 가지를 구분해야 한다

"로그인이 풀린다"는 현상 뒤에는 성격이 다른 세 가지가 섞여 있습니다.

**① 유휴 만료 (idle timeout)**  
마지막 요청으로부터 N분 동안 활동이 없으면 만료됩니다. 요청이 올 때마다 시계가 초기화되므로, 계속 사용하는 동안에는 풀리지 않습니다. 대부분의 서버가 기본 제공하는 방식입니다.

**② 절대 만료 (absolute timeout)**  
로그인한 시각을 기준으로 N시간이 지나면 **활동 여부와 무관하게** 만료됩니다. 세션 ID가 무한정 유효하게 남는 것을 막는 장치입니다. 다만 이건 기본 제공되지 않는 경우가 많아, 로그인 시각을 세션에 저장해 두고 매 요청마다 경과 시간을 검사하는 코드를 직접 작성해야 합니다.

**③ 쿠키 만료**  
`Max-Age`를 지정하지 않은 쿠키는 브라우저 용어로 "세션 쿠키(session cookie)"라 부릅니다 — 여기서 "세션"은 지금까지 이 글에서 말한 서버의 로그인 세션이 아니라, **브라우저 창이 열려 있는 동안**이라는 완전히 다른 의미입니다. 같은 단어라 헷갈리기 쉬운데, **브라우저 용어의 "세션 쿠키"와 서버의 "세션 만료"는 서로 별개입니다.**

③을 특히 주의해야 합니다. 브라우저에서 쿠키가 사라져도 **서버 저장소의 세션은 그대로 살아 있습니다.** 사용자 눈에는 로그아웃된 것처럼 보이지만 세션은 유휴 만료 시간까지 남아 있습니다. 그래서 진짜 로그아웃은 쿠키를 지우는 게 아니라 **서버가 세션을 파기하는 것**이어야 합니다.

그리고 이 지점이 세션 방식의 뚜렷한 강점으로 이어집니다. **서버가 저장소에서 세션을 지우면 그 즉시 무효**가 되므로, 특정 계정을 즉시 차단하거나 전체 로그아웃을 강제할 수 있습니다. 상태를 토큰 안에 담는 방식에서는 한 번 발급한 것을 만료 전에 되돌리기가 훨씬 까다롭습니다.

## 8. 자동 전송의 대가: CSRF

3절에서 "브라우저가 자동으로 붙여 보낸다"고 했습니다. 문제는 **그 자동 전송에 조건이 거의 없다는 것**입니다. 요청이 어느 페이지에서 출발했든, 목적지가 해당 도메인이면 쿠키가 실립니다.

그래서 공격자가 만든 페이지에 이런 폼을 심어두고 피해자가 방문하게 만들면,

```html
<form action="https://example.com/withdraw" method="POST">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.forms[0].submit()</script>
```

브라우저는 **피해자의 세션 쿠키를 성실하게 붙여서** 요청을 보냅니다. 서버 입장에서는 정상 로그인한 사용자의 정상 요청과 구분되지 않습니다. 이것이 **CSRF(Cross-Site Request Forgery)** 입니다.

토큰을 `Authorization` 헤더에 직접 담는 방식은 이 공격에 구조적으로 강합니다. 헤더는 자동으로 붙지 않으니, 공격자가 만든 페이지의 요청에는 토큰이 실리지 않기 때문입니다. **쿠키를 쓴다면 CSRF 대응은 선택이 아니라 필수 구현 항목입니다.**

대응은 두 층으로 합니다.

**1차 방어선: `SameSite` 속성** — 다른 사이트에서 출발한 요청에 쿠키를 붙이지 않도록 브라우저에 지시합니다.

| 값 | 동작 |
| --- | --- |
| `Strict` | 외부 출처 요청에는 일절 붙지 않습니다. 외부 링크로 들어오면 로그인이 풀린 것처럼 보입니다 |
| `Lax` | 최상위 내비게이션(링크 클릭 등)에만 붙고, 위 예시 같은 POST에는 붙지 않습니다 |
| `None` | 항상 붙습니다. `Secure`가 필수입니다 |

`Lax`가 보안과 사용성의 합의점이라 대부분의 브라우저에서 기본값이 되었습니다.

### `SameSite`만으로는 부족한 이유

앞선 시뮬레이터에서 `Lax`가 공격을 막아내는 걸 봤지만, 이것만 믿고 넘어가면 안 됩니다. `SameSite`는 **1차 방어선**일 뿐, 완전한 CSRF 대책이 아닙니다.

- **`Lax`는 GET 최상위 내비게이션을 허용합니다.** 링크 클릭 같은 이동에는 쿠키가 그대로 붙습니다. 서버가 `GET /delete?id=1`처럼 **GET 요청만으로 상태를 바꾸는** 엔드포인트를 두고 있다면(REST 관례 위반이지만 실제로 종종 있습니다), `Lax`로는 막지 못합니다.
- **서브도메인은 "같은 사이트"로 취급됩니다.** `SameSite`의 판정 기준은 등록 가능 도메인(eTLD+1) 단위입니다. `evil.example.com`이 `app.example.com`을 공격하는 시나리오는 여전히 통과합니다. 서브도메인 하나가 뚫리면 전체가 위험해집니다.
- **구형 브라우저는 이 속성 자체를 무시할 수 있습니다.** `SameSite`는 브라우저 기능이라, 브라우저가 지원하지 않으면 보호도 없습니다.
- **애초에 `Lax`는 "차단"이 아니라 "완화"를 목표로 만들어졌습니다.** 브라우저 벤더가 생태계 전체의 기본 위험도를 낮추려는 조치이지, 개별 서비스의 보안 요구사항까지 책임지는 장치가 아닙니다.

그래서 `SameSite`만으로 안심하면 안 되고, **서버가 직접 검증하는 2차 방어선**이 하나 더 필요합니다.

**2차 방어선: CSRF 토큰** — 서버가 예측 불가능한 값을 내려주고, 상태를 바꾸는 요청에 그 값을 함께 요구합니다. 공격자의 페이지는 그 값을 알 수 없으므로(같은 출처 정책 때문에 응답 본문을 읽을 수 없습니다) 위조 요청을 만들 수 없습니다.

아래는 `SameSite`가 뚫린 최악의 상황 — 쿠키가 그대로 첨부되는 경우 — 을 가정하고, CSRF 토큰만으로 방어가 되는지 확인해 보는 시뮬레이터입니다. "토큰 검사"를 꺼보면, 쿠키만으로는 막을 수 없다는 것도 함께 확인할 수 있습니다.

## 9. 세션을 어디에 저장하는가

서버가 상태를 갖는다는 건, 그 상태를 **둘 곳**이 필요하다는 뜻입니다.

| 저장소 | 특징 |
| --- | --- |
| 서버 메모리 | 가장 빠르고 설정이 필요 없습니다. 서버를 재시작하면 전부 사라집니다 |
| 데이터베이스 | 재시작에도 유지되지만 매 요청마다 조회 비용이 발생합니다 |
| Redis 등 외부 저장소 | 빠르면서 여러 서버가 공유할 수 있습니다. 인프라 구성 요소가 하나 늘어납니다 |

기본값인 메모리 저장이 문제가 되는 순간은 **서버가 두 대 이상이 될 때**입니다. A 서버에서 로그인한 사용자의 다음 요청이 B 서버로 라우팅되면, B에는 그 세션이 없으니 인증이 풀립니다. 세션 방식이 "확장에 불리하다"고 이야기되는 이유가 이것입니다.

해결책은 세션 저장소를 서버 밖으로 빼는 것입니다. 여기서 눈여겨볼 점은, **그렇게 보완해도 여전히 세션 방식이라는 것**입니다. 설계가 뒤집히지 않고 저장 위치만 바뀝니다.

## 10. 정리

지금까지의 내용을 한 장으로 줄이면 이렇습니다.

- HTTP는 무상태라서, 매 요청마다 "아까 그 사람"임을 증명할 표식이 필요합니다
- 쿠키는 **전달 수단**, 세션은 **저장 방식**입니다. 둘은 대립하지 않고 함께 쓰입니다
- 세션 방식에서 브라우저가 들고 다니는 값은 **의미 없는 번호표**이고, 내용물은 서버에 있습니다
- 번호표를 훔치면 곧 로그인이므로, 예측 불가능한 ID와 로그인 시 재발급이 필요합니다
- `HttpOnly` / `Secure` / `SameSite` 는 설정 항목이 아니라 방어 수단입니다
- 유휴 만료, 절대 만료, 쿠키 만료는 서로 다른 개념이며, 진짜 로그아웃은 **서버가 세션을 파기하는 것**입니다
- 쿠키의 자동 전송은 편리함인 동시에 CSRF의 원인이므로 대응이 필수입니다
- 서버가 여러 대가 되면 세션 저장소를 밖으로 빼야 하지만, 그래도 여전히 세션 방식입니다

이 글은 "어떻게 동작하는가"까지만 다뤘습니다. 다음 글에서는 이 개념들을 Spring Security로 실제 구현하는 과정 — JSON 로그인 응답, 401 처리, 쿠키 속성 설정, 직접 만들어야 하는 절대 만료 — 을 코드와 함께 정리하겠습니다.

그리고 JWT를 쓰는 프로젝트를 한 번 거친 뒤에, **왜 이 프로젝트에서는 세션을 선택했는지**를 두 방식을 모두 써본 입장에서 따로 회고해 보려 합니다.
